# 第一周后续计划

## 基线状态

- 远端 `master` 已作为当前工作基线，当前分支从该提交建立，工作区保持可提交状态。
- 项目已具备 React + Three.js 前端、FastAPI 后端、AI 平面图/照片解析、二维审图、三维预览、GLB 导出、量房 JSON 导出、Docker 与基础测试。
- 后续第一周重点不再重复搭建框架，而是补齐可验收的业务闭环：证据追溯、人工修正、识别失败处理、验收样例和交付记录。

## 目标

到第一周结束，交付一个可演示、可复核、可回归验证的卫生间测量建模工作台版本。用户可以上传测量图，得到带证据来源的结构化量房数据，人工修正关键尺寸和设施，确认后生成三维预览并导出模型与 JSON。

## 工作拆分

### 第 2 天：基线梳理与验收样例

- 固定当前远端 `master` 作为第一周后续开发基线，记录 commit SHA、运行方式和测试命令。
- 建立 2-3 组脱敏演示样例说明：矩形卫生间、带门洞卫生间、带包管或凹口卫生间。
- 明确样例期望输出字段：房间轮廓、层高、门洞、固定设施、证据 bbox、缺失项与错误提示。
- 验收标准：每组样例有输入说明、期望量房 JSON 要点和可复查的异常项。

### 第 3 天：量房证据与数据结构硬化

- 检查 `MeasurementModel` 与 `RoomSpec` 的字段映射，确保墙体、门洞、设施和高度都能回溯到 evidence。
- 补充后端验证用例，覆盖墙体闭合、墙长不一致、门洞越界、低置信度证据和缺失层高。
- 统一 AI 失败时的项目状态、旧结果隔离和用户可恢复路径。
- 验收标准：后端测试覆盖关键异常；失败识别不会污染已确认模型；导出的量房 JSON 可独立校验。

### 第 4 天：人工审图与修正闭环

- 优化二维审图中墙体、门洞、设施的选中和编辑流程，避免用户只能拖动设施而无法快速修正关键尺寸。
- 增加或完善保存前校验提示，把错误、警告和缺失项按可操作对象呈现。
- 校验撤销、重做、保存、确认数据和切换项目时的状态一致性。
- 验收标准：用户不依赖重新识别即可修正主要尺寸；有错误时不能误进入最终建模状态。

### 第 5 天：三维预览、导出与演示交付

- 核对 Three.js 坐标、比例、门洞和固定设施尺寸，确保 GLB 与同版量房 JSON 一致。
- 跑通本地生产构建、后端测试、前端测试和 UI 冒烟验证。
- 形成演示脚本：创建项目、上传测量图、解析、修正、确认、预览、导出 JSON/GLB。
- 验收标准：演示脚本可按步骤复现；验证命令全部通过或列明剩余阻塞。

## 风险与处置

- AI 多模态输出不稳定：保留原始脱敏 trace，失败状态不覆盖旧模型，关键尺寸必须可人工修正。
- 非矩形轮廓识别偏差：优先补验证样例和人工修正能力，再扩大自动识别范围。
- 三维模型与 JSON 不一致：以同一版 `MeasurementModel`/`RoomSpec` 为源，导出前跑一致性校验。
- 样例数据不足：若缺少可用脱敏图纸，应先用合成样例覆盖流程，再等待真实样例补充。
